## 3. Part B — new findings

### P0 — critical

#### FIX-20 · "Log Repayment" has never worked: insert names a non-existent column and omits NOT NULL `paid_by_id`
**Severity:** CRITICAL (dead money feature; dashboard/analytics debt overstated after any real-world repayment) · **Model:** Sonnet · **File:** `src/app/(app)/loans/page.tsx`

**Verified root cause.** The table is (`supabase/FRESH-INSTALL.sql:171-179`, identically `schema.sql:156-166`):
```sql
paid_by_id    UUID NOT NULL REFERENCES auth.users(id),   -- no default
payment_date  DATE NOT NULL DEFAULT CURRENT_DATE,
```
The insert (`loans/page.tsx:122-125`) sends `repayment_date` (column doesn't exist)
and no `paid_by_id`:
```ts
const { error } = await supabase.from('loan_repayments').insert({
  loan_id: loan.id, amount: amt,
  repayment_date: repayDate, notes: null,
} as any)
```
The `as any` cast is exactly what hid this from `tsc` — the type
(`database.types.ts:152-160`) correctly says `payment_date` + required `paid_by_id`.
Every attempt fails with PGRST204 (unknown column). Post-FIX-19 the user at least sees
"Could not save repayment: …"; the row never lands, repayment progress bars are always
0, loan status never flips to partial/cleared, and the dashboard "You owe" keeps
counting fully-repaid loans.

**Fix spec:**
1. Change the payload to `{ loan_id: loan.id, amount: amt, paid_by_id: userId, payment_date: repayDate, notes: null }` (the page already holds `userId` in state; the RLS insert policy requires `auth.uid() = paid_by_id` — `loans-shared.sql:41-42`).
2. **Delete the `as any` cast** so the type checker guards this payload forever.
3. Leave everything else (validateAmount, error surfacing, status update) as is — it's correct.

**Verify:** `npx tsc --noEmit` → 0. On localhost: log a repayment on a loan → no alert,
row visible in `loan_repayments` (Supabase table editor) with `paid_by_id` set,
progress bar moves, status flips to `partial` (or `cleared` at full amount), dashboard
"You owe" drops accordingly.

### P1 — high (integrity / durability)

#### FIX-21 · PostgREST 1000-row default silently truncates backups and all-time totals
**Severity:** HIGH (silent data loss on the exact 2-5-year horizon this app targets) · **Model:** Sonnet · **Files:** `scripts/backup.mjs`, `src/app/(app)/settings/page.tsx`, plus one owner dashboard action

**Verified.** Supabase's PostgREST `max-rows` defaults to **1000 per request**. Every
`select('*')` in the app is unpaginated: `backup.mjs:77`, Settings `exportData`
(`settings/page.tsx:153`) and `exportExcel` (`:175`), and every page's `load()`
(dashboard `expensesData`, sadaka entries, joint txns…). At 2-5 users-years,
`expenses` (a few entries/day) crosses 1000 first — after that, `npm run backup`
writes a JSON that *looks* complete (`✓ expenses: 1000`), the Settings backup exports
1000 rows, and the dashboard's all-time expense arm silently plateaus. A restore from
such a backup permanently loses the excess rows.

**Fix spec:**
1. `backup.mjs`: page each table with `.range(from, from + 999)` in a loop until a
   short page returns; concatenate. (~8 lines, no new deps.)
2. `settings/page.tsx` `exportData`/`exportExcel`: same loop (extract one
   `fetchAll(table)` helper inside the file — two callers, no new abstraction beyond that).
3. **Owner action (belt + braces):** Supabase dashboard → Settings → API → set
   "Max rows" to **10000**. This also protects every page's totals for years without
   touching 12 files. Document it in `MAINTENANCE.md`'s yearly checklist.
4. Do NOT paginate every page's `load()` — at 2-user volume with max-rows raised to
   10k, that's years of headroom; note it as a `// ponytail:` ceiling comment in
   `dashboard/page.tsx` instead.

**Verify:** temporarily set `.range()` page size to 5 in `backup.mjs` and run
`npm run backup` against live data → row counts must match Supabase table editor
exactly; restore page size.

#### FIX-22 · Settings export/reset ignore errors: a "successful" backup can contain silently-empty tables
**Severity:** HIGH (the monthly backup ritual in MAINTENANCE.md is the user's only safety net) · **Model:** Haiku · **File:** `src/app/(app)/settings/page.tsx`

**Verified.** `exportData` (`:152-155`) and `exportExcel` (`:174-176`) do
`const { data } = await supabase.from(t).select('*'); backup.tables[t] = data ?? []` —
a network blip / Supabase wake-up mid-export writes `[]` for that table with no
warning, and the file downloads looking complete. `resetData` (`:199-202`) ignores
every delete's error, then alerts "All test data cleared" regardless.

**Fix spec:** in all three loops capture `{ data, error }`; on any error abort with
`alert('Backup failed at table X: … — file NOT saved, try again')` (export) or list
the failed tables (reset) instead of pretending success. Fold into the same commit as
FIX-21's `fetchAll` helper — it should throw on error.

**Verify:** DevTools offline mid-export → alert appears, no file downloads. Online →
file contains all 18 tables with correct counts.

#### FIX-23 · Shared income added by one brother is invisible to the other (RLS) — silently defeats FIX-07
**Severity:** HIGH (wrong hero number whenever shared income is actually used) · **Model:** Haiku creates the SQL, **owner runs it**; owner should confirm intent first · **Files (new):** `supabase/shared-income-visibility.sql`; also append to `FRESH-INSTALL.sql`

**Verified.** `income_projects` RLS is strictly owner-scoped — `FOR ALL USING
(auth.uid() = owner_id) WITH CHECK (…)` (`income-upgrades.sql:15-17`,
`FRESH-INSTALL.sql:709-710`); no migration widens SELECT. But three code paths assume
shared rows are visible to both:
1. `dashboard/page.tsx:97-99` counts `ownership === 'shared'` rows at 50% (FIX-07) —
   for a shared income the **brother** added, RLS returns nothing, so my half is 0,
   while the sadaka trigger (SECURITY DEFINER, bypasses RLS) still creates **my**
   obligation. When I pay it, sadaka subtracts from a hero that never added the income
   half — the exact FIX-02 asymmetry through the RLS door.
2. `SadakaForm.tsx:75-77` picker filter `i.owner_id === user.id || i.ownership === 'shared'`
   — the second branch is dead; I can't link my payment to the brother's shared income.
3. `sadaka/page.tsx:50` income-names map — my obligation card shows generic
   "Sadaka obligation" instead of the income name.

Mitigating: the owner stated (FIX-07 note) incomes are normally separate, so shared
rows are rare — but the ownership picker offers "Shared" to both users, so the state
is one tap away.

**Fix spec:** new migration adding a **SELECT-only** widening (writes stay owner-only —
this ADDS a policy, does not weaken any write path):
```sql
DROP POLICY IF EXISTS "income_shared_select" ON public.income_projects;
CREATE POLICY "income_shared_select" ON public.income_projects
  FOR SELECT USING (auth.uid() = owner_id OR ownership = 'shared');
```
(The existing `income_own` FOR ALL policy stays; policies are OR-ed.) Append the same
block to `FRESH-INSTALL.sql`, add as migration **20** in PROJECT_STATUS.md, owner runs
it. Ask the owner first: *"Should a 'Shared' income be visible to both of you (it
already splits 50/50 in both dashboards and sadaka)?"* — expected yes, it's what FIX-07
already assumes.

**Verify (owner, test mode):** Brother A adds a shared income → Brother B's dashboard
"In hand"/"Awaiting" moves by half; B's sadaka picker lists it; B's obligation card
shows its name. B still cannot edit/delete it (only A can).

#### FIX-24 · SadakaForm edit: flipping status between payment and obligation leaves `amount_given` stale
**Severity:** HIGH (silent wrong pending number via a plausible correction flow) · **Model:** Sonnet · **File:** `src/components/sadaka/SadakaForm.tsx`

**Verified residual of FIX-17.** The delta logic (`:102-128`) handles
"status unchanged" perfectly, but when `statusChanged` is true:
- **Payment → pending** (user recorded an "Advance Given" by mistake and fixes it —
  reachable because only `status === 'given'` is locked, `sadaka/page.tsx:335`; an
  `advance_given` row is editable): `willBePayment` = false → payload sets
  `amount_owed = amount`, `status = 'pending'` but **omits `amount_given`** — the row
  becomes owed X / given X, a self-cancelling obligation. Pending doesn't rise; the
  phantom "given" amount stays in the Given totals forever.
- **`partially_given` obligation → given** via the select: payload becomes a pure
  payment (`amount_owed: 0, amount_given: <form amount>`), erasing the obligation and
  spilling its previously-linked payments into advance credit — pending drops by more
  than was actually given.

**Fix spec (surgical, keep the existing structure):**
1. In the `statusChanged && !willBePayment` case (payment being demoted to obligation):
   add `payload.amount_given = 0; payload.date_given = null` — the user is saying
   "this money was never given".
2. In the `statusChanged && willBePayment && !wasPayment` case (obligation → payment):
   **block it** when the engine shows anything already given toward it — show
   `setError('This obligation already has payments — use "Mark as Given" on the card instead.')`
   and return. (The form already imports the outstanding map; a simple
   `Number(editItem.amount_given) > 0` check plus the existing card flow covers the rest.)
3. Status-unchanged edits: leave exactly as they are.

**Verify:** test mode — record Advance Given 200, edit → set status Pending, save →
row must be owed 200 / given 0, header Pending rises by 200. Create obligation 500,
pay 200 toward it, edit the obligation → select "Already Given" → must refuse with the
message; "Mark as Given" on the card still works and books only the remaining 300.

#### FIX-25 · Zakat page: failed rates read silently computes nisab on hardcoded defaults with no banner
**Severity:** HIGH (fiqh verdict on invisible-fallback numbers; fires on the guaranteed Supabase-resume scenario) · **Model:** Haiku · **File:** `src/app/(app)/zakat/page.tsx`

**Verified.** `load()` (`:36-51`) never checks errors. If the `rates_cache` read fails
(paused project waking, network blip), `rates` stays at the hardcoded defaults
(`:20` — gold 472 / silver 5.9 / pkr 0.013) and `ratesUpdatedAt` stays `null` — which

can Calculate and Save a WAJIB/not-WAJIB verdict against defaults with zero indication
anything failed. Snapshots list also renders empty (fake empty state — the FIX-18
class; this page was not on FIX-18's list because it has no EmptyState).

**Fix spec:** capture the errors of the three parallel reads; if the rates read
errored OR returned no rows, render the existing amber banner style with
*"⚠ Couldn't load live rates — using built-in defaults. Retry before trusting the
nisab."* (reuse `LoadError` for the full-page case when the snapshots/profile reads
fail, matching the 12 patched pages).

**Verify:** unreachable `NEXT_PUBLIC_SUPABASE_URL` locally → zakat page shows the
banner/LoadError, not a silent calculator; restore → banner gone, live rates shown.
